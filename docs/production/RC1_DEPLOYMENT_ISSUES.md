# RC1 Deployment Issues

Recorded per the deployment issue policy: every finding is logged here, including a statement that
no NEW code-level fix was attempted in this phase. No hotfix implementation is mixed into this
deployment phase.

## Issue 1 — PWA manifest references missing icon files

- **Symptom:** `manifest.webmanifest` (generated by `vite-plugin-pwa`, configured in `vite.config.*`)
  declares two icons, `pwa-192x192.png` and `pwa-512x512.png`. Neither file exists in `public/` at
  the RC1 commit, and neither exists in the built `dist/` output. Requesting either path on the
  live production URL returns the SPA HTML shell (`Content-Type: text/html`) via the catch-all SPA
  redirect, not a real image.
- **Severity:** Low–Medium. Cosmetic/PWA-installability impact only (browsers may show a generic or
  missing icon when the app is "installed" to a home screen / app launcher). No functional, data,
  or security impact.
- **Reproduce:** `curl -I https://pharmapluse.netlify.app/pwa-192x192.png` → `200`,
  `Content-Type: text/html` (a real PNG would return `image/png`).
- **Pre-existing, not a regression:** confirmed identical behavior on the *previous* live
  production deploy (`6a235b65ece4e800088186ac`, commit `981a6dd8a0d64cb537082b517c12c4b803b12864`,
  `main`) before this phase's deployment — the gap predates RC1 and predates this deployment
  action.
- **Rollback need:** None. Rolling back would not remove this issue, since it exists in the
  previously-live build too.
- **Stop before code change:** Per this phase's explicit scope ("no app code modification"), no
  icon asset was added and no `vite.config` change was made. This requires either generating the
  two missing PNG icon assets or removing the icon entries from the manifest — a small, separate,
  owner-approved fix, not a deployment action.
- **Action requested:** Separate hotfix authorization needed if this is to be fixed.

## Issue 2 — No CSP / X-Frame-Options / X-Content-Type-Options response headers

- **Symptom:** Only `Strict-Transport-Security` is present in the live response headers (Netlify's
  default). No `Content-Security-Policy`, `X-Frame-Options`, or `X-Content-Type-Options` header is
  configured.
- **Severity:** Low (defense-in-depth gap, not an active exploit path observed). Unchanged from the
  previous production deploy — `netlify.toml` has never defined a `[[headers]]` block in this
  program.
- **Reproduce:** `curl -I https://pharmapluse.netlify.app/` and inspect headers.
- **Pre-existing, not a regression.**
- **Rollback need:** None.
- **Stop before code change:** Adding a `[[headers]]` block to `netlify.toml` is a configuration
  change outside this phase's "no app code modification" boundary.
- **Action requested:** Separate hotfix authorization needed if this is to be hardened.

## Issue 3 — Local build performed on Node v24.15.0 vs. configured `NODE_VERSION=20.19.0`

- **Symptom:** The deployment build in this phase ran in a local CLI worktree using the locally
  installed Node (`v24.15.0`), not Netlify's own build image, which would use the site's configured
  `NODE_VERSION` (`20.19.0`).
- **Severity:** Informational only. The build succeeded with no errors on the newer local Node
  version; no Node-version-dependent failure was observed.
- **Rollback need:** None.
- **Action requested:** None — recorded for awareness. A future Git-triggered build (if `main` is
  ever updated to include RC1) would use the configured `20.19.0` image as normal.

## No other issues found

No secret, credential, personal-data, or service-account leakage was found beyond the two items
above. No Firestore/Auth mutation occurred. No routing, redirect, or SPA-fallback defect was found.
