# DX-8 / DX-9 — Template System Hardening & Data Exchange Studio Closure

## Scope

This bundle implements exactly two phases on top of the already-closed
DX-1 through DX-7 work (Organization Onboarding, KPI Registry & Targets,
Branch/Pharmacist Actuals & large-file engine):

- **DX-8 — Template System Hardening**: one centralized template
  catalog, explicit template version metadata, workbook quality
  (autofilter + column widths), and a Template Library section in the
  Studio UI.
- **DX-9 — Data Exchange Studio Closure & Certification**: a closure
  audit across every domain, an import history view, a standardized
  user-facing error taxonomy, and backward-compatibility verification.

No new import domain was added. DX-10 (Export Studio) was explicitly
out of scope and was not started.

## DX-8 — Templates

### Catalog

`src/services/dataExchange/templateCatalog.ts` is a thin index over the
real generator functions in `templateGenerator.ts` — it does not
duplicate any template-building logic. It exposes exactly 6 entries,
grouped for the UI:

| Group | Templates |
|---|---|
| Organization Setup | Organization Onboarding (Groups, Branches, Pharmacists, Assignments — one multi-sheet workbook) |
| KPI & Targets | KPI Registry, Branch Targets, Pharmacist Targets |
| Actuals | Branch Actuals, Pharmacist Actuals |

The Organization Onboarding template did not exist before this bundle —
DX-2/DX-3 had full adapters and an orchestrator for these four domains
but no downloadable workbook. `buildOrganizationOnboardingTemplate()`
closes that gap, built from the same `HEADER_ALIASES` the adapters
already use and the same `SHEET_NAME_ALIASES` the orchestrator already
recognizes — so the new template and the existing import path agree by
construction, not by hand-matching.

### Version metadata

Every generated workbook has a `Metadata` sheet (Field/Value rows):
Template Name, Template Version, Import Domain, Generated By, Expected
Sheet, Date Format, Month Format (where applicable), Identifier Rules.

`TEMPLATE_VERSION` is a single string constant (`'1.0'`) — the smallest
maintainable versioning model, per instruction, rather than a migration
framework. `templateVersionGuard.ts` enforces it on import:

- A workbook with **no** Metadata sheet (every file generated before
  DX-8) is treated as a **supported legacy version** — never rejected.
- A workbook with an **explicit, unrecognized** version string is
  rejected with a clear, non-crashing message asking the user to
  download a fresh template — never a stack trace or generic error.
- The currently supported version is always exactly `[TEMPLATE_VERSION]`
  (`SUPPORTED_TEMPLATE_VERSIONS`).

This check runs in `DataExchangeStudioPage.jsx` immediately after
`XLSX.read()`, before any row is parsed into a job, in all three upload
paths (Organization Onboarding, KPI/Targets, Actuals).

### Workbook quality

`applyDataSheetQuality()` sets `!autofilter` and `!cols` (auto-sized
column widths) on every data sheet — both are genuinely supported by
the installed SheetJS Community Edition. Frozen header panes and in-cell
data-validation dropdown lists are **not** supported for writing in this
library version (confirmed by reading the writer source —
`write_ws_xml_sheetviews()` never emits `pane`/`freeze` elements, and
dropdown validation requires the Pro build). Allowed-values guidance is
instead written as plain text in each template's Instructions sheet,
sourced from the real `ALLOWED_VALUES` enum constants — never hardcoded
strings that could drift from the adapters' actual accepted values.

No production data, real names, emails, branch details, credentials, or
internal document IDs appear in any template — every example row uses
placeholder values (e.g. `pharmacist@example.com`, `EMP1024`).

### Template Library UI

`TemplateLibrarySection` (in `DataExchangeStudioPage.jsx`) renders the
catalog grouped by Organization Setup / KPI & Targets / Actuals, each
entry showing name, version, expected sheet, and a Download button
wired directly to the catalog's real `download()` function. It replaces
the previous per-section inline "Download template" buttons, which now
point the user back to this single library instead of duplicating
download logic in three places.

## DX-9 — Closure

### Closure matrix

See `DATA_EXCHANGE_CLOSURE_MATRIX.md` for the full per-domain matrix.
Summary: all 9 domains are certified for upload → validate → preview →
confirm → commit → audit. Only Branch/Pharmacist Actuals have
chunking/progress/retry/resume/cancel — this is documented as a known,
intentional limitation (these are the only domains built for
large-file volume), not silently presented as available everywhere.

### Import history

`ImportHistorySection` (admin-only) lists the most recent `import_jobs`
documents — date/time, domain, file name, status, total/committed/
failed row counts — via the new `listRecentImportJobs()` query in
`firestoreStagingRepository.ts`. No raw row payloads, stack traces, or
uncontrolled document IDs are rendered; only the job summary fields
already present on `ImportJob`.

`DataExchangeHealthSummary` (admin-only, optional) shows five compact
counts derived from the same history fetch plus the static catalog
size: supported domains, completed/failed/retryable/active jobs. It is
not an analytics module — five numbers, no charts, no drill-down.

### Error taxonomy

`importErrorTaxonomy.ts` maps every real `ValidationIssue.code` emitted
by the adapters (enumerated by grepping `code: '...'` across
`adapters/*.ts` and `importJobEngine.ts`) into one of the 11
task-specified categories: File Format Error, Template Version Error,
Missing Required Column, Invalid Identifier, Duplicate Row, Existing
Record Conflict, Permission Denied, Stale Preview, Partial Commit
Failure, Retry Not Safe, System Error. An unmapped code falls back to
System Error rather than throwing — the underlying technical code and
message are still preserved on the row for audit/support purposes; the
taxonomy only adds a friendly label on top.

### Backward compatibility

DX-1 through DX-7 `import_jobs` documents have no `Metadata` sheet
concept at all (it didn't exist yet) — `templateVersionGuard.ts`'s
legacy-is-supported rule means a pre-DX-8 template still imports
without any version-related rejection. No historical `import_jobs`
documents were rewritten or migrated.

### Security

No Firestore rule was broadened. `import_jobs` read/write rules remain
`createdBy == uid() || isAdmin()` (read) and admin-only create/update.
`listRecentImportJobs()` performs an unfiltered `orderBy` query and
relies on the **caller** (the admin-only Studio page) to gate access —
documented inline in `firestoreStagingRepository.ts` — with the
Firestore rule itself as the defense-in-depth backstop for any other
caller. No new collections were added. No audit marker
(`importedViaDataExchange`/`importBatchRef`) field became user-settable
by this bundle — those fields are set server-side by the existing
commit paths only.

### Performance

No change to the tested limits documented in
`DX6_DX7_ACTUALS_LARGE_FILES_BUNDLE.md`. Template generation, version
checking, and catalog lookups are synchronous, in-memory, and add no
measurable overhead to the existing import flows — confirmed by the
build and full test suite completing in the same order of magnitude as
prior bundles. The 2,000-row practical ceiling is unchanged and is not
claimed to be higher.
